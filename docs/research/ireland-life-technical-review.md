# Ireland Life technical review

**Scope:** Architecture and implementation readiness review of the supplied Architecture Document v1.0 and TRD v2.0. Both source documents are drafts dated 2026-10-08. This is a review of their written proposals; it does not establish that the proposed stack, code examples, or provider claims are current or working. The workspace also contains public rendering chunks and a Lagos/Abuja map prototype; their suitability for Ireland scenes needs an explicit reuse assessment.

**Documents read in full:** `/Users/therealmodey/ireland-life-architecture.md` (615 lines) and `/Users/therealmodey/ireland-life-trd-v2.md` (1,486 lines).

## Assessment

The documents give a broad feature map and a useful first pass at game entities, APIs, auth, monitoring, and deployment. The TRD adds SQL table definitions, endpoint examples, a state shape, and security/performance sections. They are enough to estimate discovery and prototype work, but not enough to implement a production multiplayer game. The supplied documents do not specify a renderer or scene/asset production pipeline; the existing rendering chunks and map prototype are useful evidence for a reuse spike, not proof of an Ireland-ready renderer or scene pipeline. The save endpoint accepts the client’s complete game state, and the relationship between per-player simulation and a shared real-time world is unresolved.

A coherent baseline would be a React/Next.js client for menus, HUD, and phone UI; a separate, explicitly selected 3D renderer behind `MapView`; versioned, optimized city scene bundles served from object storage/CDN; and a server-side command API that owns consequential simulation state. PostgreSQL should be the durable source of truth, with transactions for money/state transitions and append-only event/transaction records. Redis should be introduced only for measured session/rate-limit/cache needs. Begin with single-player or asynchronous social features and the specified 15-second world poll; add sockets or shared simulation only after the multiplayer model and load needs are defined. Keep the client store as a presentation cache, not an authority.

## Severity-ranked findings

### Blockers before production implementation

1. **The client can authoritatively rewrite game state.** Architecture §3.1 says the server validates and saves after optimistic local updates (Architecture lines 240–261). TRD §3.3 makes `PUT /api/save` accept the extended game object (lines 458–514), while §5.2 exposes `updateGame` and posts the client object (lines 988–1045). There is no field allowlist, server-side recomputation, command/event contract, or conflict/merge policy. A client can plausibly forge balances, visa state, skills, and outcomes. Specify command endpoints (e.g. `applyVisa`, `exchangeCurrency`, `travel`) that validate preconditions and atomically mutate authoritative state; restrict generic saves to non-consequential preferences or remove them.

2. **The supplied packet lacks a 3D rendering and scene production specification.** The architecture names a `MapView` but no graphics engine, rendering mode, scene format, asset pipeline, ownership/licensing rules, or mobile/low-end fallback (Architecture §2.1, lines 142–171). TRD §5.1 repeats a generic `MapView` hierarchy without implementation detail (lines 944–986); S3/CDN is only named for assets (TRD §1.1, lines 98–110). The workspace’s public rendering chunks and Lagos/Abuja map prototype should inform the choice and reuse spike; their Ireland suitability is not established here. The Lagos scrape alone cannot specify a Dublin/Ireland scene. Decide whether the experience is 2D, 2.5D, or 3D; assess the existing renderer and map assets; define the Ireland scene source, optimization, versioning, and device-quality budgets before city production.

3. **“Real-time” and multiplayer semantics are contradictory or undefined.** TRD §1.2 specifies polling every 15 seconds (lines 115–136), while Architecture §3.1 depicts state broadcasts to clients (lines 238–261). TRD §3.3 includes `online`, `players`, `guests`, and `inbox` world data but supplies no ownership, presence, consistency, or synchronization protocol (lines 516–537). The ERD includes messages and transactions, yet they have no corresponding DDL in §2.2 (lines 188–239). Decide whether this is per-user simulation with occasional world snapshots, asynchronous social play, or shared live sessions; then define authoritative world state, visibility, conflict handling, presence, and delivery mechanism. The current docs do not support a multiplayer implementation estimate.

4. **Core persistence and state ownership are internally inconsistent.** TRD §2.3 stores Ireland state inside `game_saves.game` JSONB (lines 338–379) and §4.1 repeats those fields in `GameState` (lines 744–891), but §2.2 also normalizes visa applications, exchanges, japa attempts, and immigration status (lines 241–336). TRD §11.1 separately proposes adding overlapping columns to `game_saves` (lines 1349–1376). This creates multiple sources of truth for status, balances, and history. Choose which facts are normalized and authoritative versus derived/cached in JSON; define constraints, uniqueness, versioning, migration/backfill, and transactional write boundaries. Core `users`, `game_saves`, and `sessions` schemas are shown only in an ERD, not runnable DDL (TRD §2.1, lines 188–239).

5. **Backend parity and migration are not established by the documents.** The architecture and TRD describe the proposed stack as “same as Lagos Life” (Architecture §1.2, lines 66–80; TRD §1.2, lines 115–136), but do not verify the original service’s schema, API behavior, or deployment contract. TRD §11.1 contains placeholder `CREATE TABLE ... (...)` statements and uses both `updatedAt` and `updated_at` names (lines 1349–1376). Inspect the original repository/backend and current schema if Ireland Life must extend or migrate the actual Lagos Life service, or if exact backend parity is a requirement. A standalone Ireland Life implementation can choose a new backend without that access. In either case, the excerpts and code snippets are design examples, not proof of working code.

### High-priority decisions and corrections

6. **Currency and balance math disagree.** TRD’s sample has both `fxRate: 1.55` and `fxRate: 1500` (TRD §2.3, lines 338–379, and §3.3, lines 464–501), while the exchange example divides NGN 150,000 by a rate of 1,562.50 to produce EUR 96 (TRD §3.4, lines 676–704). TRD §11.1 also defaults `fx_rate` to 1500 (lines 1349–1369). The `currency` field permits only one currency despite an NGN↔EUR exchange flow. Define the rate direction and source, use integer minor units or an explicit decimal policy, and decide whether balances are dual-wallet or converted-on-trade. Never accept the exchange rate, outcome, or resulting balance from the client.

7. **State machine, API response, and SQL statuses conflict.** The sample visa application response says `approvalChance` is returned to the client (TRD §3.4, lines 541–567), while the SQL stores a chance and decision state server-side (TRD §2.2, lines 243–270); application sample `visa.status: "valid"` does not match the SQL status check (`pending/approved/rejected/expired/revoked`) (TRD §2.3, lines 342–379 and §2.2, lines 243–260). Immigration transition rules say a Garda arrest/deportation returns the player to `citizen`/Lagos, while the status model has only `citizen`, `visa`, `undocumented`, and `regularised` (TRD §4.1–4.3, lines 836–940). Define canonical enums and transitions, distinguish visa application from visa grant, and state how location/travel is represented. Avoid exposing random decision odds if players should not be able to game them.

8. **Important mutations lack transactional/idempotency requirements.** Visa, japa, FX, and travel examples have no idempotency key, transaction boundary, retry semantics, or concurrent-request behavior (TRD §3.2–3.5, lines 414–740). In particular, an exchange or japa retry after a timeout could double-charge or reroll. Add idempotency and atomic balance-ledger updates, with a durable result replayed for duplicate requests. Clarify which values are game fiction and which Stripe/payment flows involve real money; “Stripe replaces Bachs” is stated without a product/payment scope (Architecture §1.2, lines 66–80; TRD §1.2, lines 115–136).

9. **Auth and privacy controls are incomplete for the stated product.** The docs specify HTTP-only/SameSite cookies, bcrypt, and rate limits (Architecture §5, lines 374–440; TRD §6.1–6.5, lines 1138–1179), but do not define session token storage/rotation/revocation, secure cookie settings by environment, CSRF defenses for state-changing requests, account recovery/verification, or authorization details for shared/social records. “SameSite=Strict” alone is not a complete CSRF design. LogRocket session replay and GDPR/data minimization are both proposed without redaction/consent/retention policy (TRD §1.1 and §6.5, lines 98–110 and 1173–1179). Define these before collecting real account data.

10. **Documents and privacy-sensitive game data have no lifecycle.** The visa flow accepts document names/boolean checklist flags but does not say whether users upload real files, how files are scanned/stored, or when records are deleted (TRD §2.3 and §3.4, lines 338–379 and 541–619; Architecture §2.1, lines 155–159). Decide whether this is fictional inventory only. If uploads are real, design storage, access, malware scanning, retention, deletion, and data minimization separately.

11. **Performance targets lack a workload and graphics profile.** TRD sets page load <2s, API p95 <200ms, 1,000 concurrent users, 50 DB connections, and >80% cache hit (TRD §7.1–7.2, lines 1183–1205), with DigitalOcean autoscaling and replicas described earlier (TRD §1.3, lines 138–183). There is no region, request mix, active-player definition, save/poll frequency, scene size, target phone/GPU, or measured baseline. Treat these as provisional targets; specify representative devices and gameplay/API workloads, then load-test and profile before sizing Redis, replicas, or autoscaling.

12. **Deployment examples are placeholders, not an executable release design.** The docs provide domains, a GitHub Actions YAML, App Platform action, and blue-green/rollback claims (Architecture §6, lines 444–532 and TRD §10, lines 1292–1345), but do not define separate database/environment credentials, migration ordering, health checks, secrets rotation, backup restore drills, or the actual deployment contract. Validate provider/action names and current capabilities against the chosen account and project; these claims were not independently verified here.

## Readiness by area

- **Stack and app shell:** Directionally specified (Next.js/React, Zustand, CSS Modules, PostgreSQL, Redis, DO, Cloudflare), but versions, provider fit, and current Lagos compatibility remain unverified (Architecture §1.2; TRD §1.2). Do not treat vendor/version assertions as confirmed-current.
- **Frontend 3D renderer and scenes:** Not specified enough in the Ireland documents to implement. Existing public rendering chunks and a Lagos/Abuja map prototype provide project evidence for a reuse assessment, but the packet does not define how they carry over to Ireland or specify scene assets, generation, optimization, or device fallback.
- **Backend simulation:** Feature boundaries are named, but rules (visa decisions, japa odds/consequences, FX fees/scams, regularisation, time progression) are not numerically or deterministically specified. Server ownership and command contracts need redesign.
- **Auth:** A starting policy exists, not an implementation-ready session/account lifecycle.
- **Persistence:** Partial table proposals exist, but dual JSON/relational representations, missing core DDL, and incomplete migration prevent safe schema implementation.
- **Multiplayer/realtime:** Unresolved; 15-second polling is specified but shared-world semantics and broadcast/presence behavior are not.
- **Economy integrity:** Not implementation-ready until balance units, wallet model, rate source, transaction ledger, atomicity, retries, and real-payment boundary are fixed.
- **Performance/security:** Headline targets and baseline controls exist, but workload, threat model, abuse controls, and privacy handling need concrete acceptance criteria.
- **Testing/deployment:** Test categories and a CI outline are useful scaffolding (TRD §§8–10, lines 1209–1345); they need concrete invariants, game-rule fixtures, migration rollback, security checks, device profiles, and release/restore procedures.

## Recommended staged implementation

1. **Discovery and contract:** If extending/migrating the actual Lagos Life service or requiring backend parity, inspect its repository and backend for the save schema, API/auth/social flows, providers, and deployment, then capture a compatibility matrix. For a standalone Ireland backend, define its contract directly. In either case, assess the existing rendering chunks and map prototype, decide single-player versus asynchronous social versus live multiplayer, and separate fictional currency from real payment.
2. **Renderer and asset spike:** Build one small Ireland scene from authorized/reference assets, test the selected 2D/2.5D/3D renderer on representative mobile and desktop devices, and measure bundle size, frame rate, memory, and load time. Decide scene source, versioning, CDN packaging, and quality fallback from evidence.
3. **Authoritative game vertical slice:** Implement one complete journey (for example, passport → visa application → decision → travel) using server-owned commands, deterministic rules/seed handling, idempotency, atomic balance updates, explicit state transitions, and a minimal normalized schema with versioned migrations. Keep only presentation state in Zustand.
4. **Security and data lifecycle:** Implement session lifecycle, CSRF/authorization, rate and abuse controls, audit/transaction records, privacy-safe telemetry, and document handling policy. Test forgery, replay, races, retries, and deletion/export requirements.
5. **Expand systems and social sync:** Add FX, japa, immigration and messages only after each rule and state ownership is specified. Start with the documented polling model if it meets the declared behavior; introduce realtime transport only if product requirements and load tests show polling is insufficient.
6. **Release readiness:** Establish staging and production environments, migration/rollback and restore drills, monitoring/redaction, target-device acceptance, and load tests against the chosen workload. Verify actual provider capabilities and account configuration before relying on the deployment examples.
