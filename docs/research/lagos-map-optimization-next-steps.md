# Lagos Life map clone: optimization priorities

These are source-backed opportunities, not measured bottlenecks. The parent verified the four decisive reference chunks against the live site on 2026-10-08; they are byte-identical to the saved snapshots, and the live loader chain references them. This comparison does not claim measured frame times.

| Priority | Change | Why this is a plausible win | Effort / risk | Evidence |
|---|---|---|---|---|
| 1 | Add a low-power rendering profile: lower the pixel-ratio cap on constrained devices, reduce or disable shadow maps there, and scale generated canvas textures down. | The clone always caps DPR at 2 and enables 2048² soft shadows (`main.js:7–10,20–22`). The saved public city bundle has a `LOW_POWER` branch that reduces canvas texture dimensions to half, lowers anisotropy, and skips shadow casting on instanced objects (`work/city-map-reference.js`, minified `LOW_POWER` and `InstancedMesh` paths). | Low–medium; visual quality can vary, so check desktop and mobile. | `outputs/lagos-map/src/main.js:7–10,20–22`; `work/city-map-reference.js` |
| 2 | Batch repeated Lagos scenery, beginning with the 116 estate buildings and 28 palms; consider repeating simple props after that. Reuse shared primitive geometries for the `box`, `cylinder`, and `dome` helpers. | Lagos creates an individual GLTF scene clone for each estate building and palm (`main.js:78–82`), while each primitive helper call constructs a new geometry (`main.js:26–29`). Abuja already groups geometry and uses `InstancedMesh` for roads, trees, homes, and repeated artwork (`abuja.js:8–29,38–63,69–77`). The reference bundle also uses instanced batches. This should reduce object/draw submission overhead, but actual draw-call savings depend on source GLTF mesh counts and need profiling. | Medium; preserve per-object movement, shadows, visibility, and selection behavior. | `outputs/lagos-map/src/main.js:26–29,78–82`; `outputs/lagos-map/src/abuja.js:8–29,38–63,69–77`; `work/city-map-reference.js` |
| 3 | Defer the inactive city’s construction and model loads until its first selection, or split each city into a lazy module. | `main.js` statically imports and builds Abuja while it also starts Lagos model tasks; `switchCity` only hides the inactive world (`main.js:4,72–75,88–95`). All model tasks are awaited before the loader disappears (`main.js:142`). The original bundle includes a lazy scene chunk (`city-map-reference.js`, `lazy` path). | Medium–high; affects startup sequencing, labels, direct `?city=abuja` entry, and the shared place list. | `outputs/lagos-map/src/main.js:4,72–75,88–95,142`; `work/city-map-reference.js` |
| 4 | Avoid bounding-box recomputation for every clone by caching each loaded model’s local bounds/normalization data. | `modelCache` caches the loaded GLTF scene, but `addModel` clones it and runs `Box3.setFromObject` for each placed copy (`main.js:42–43`). Repeated models make this redundant startup work. | Low; confirm bounds remain valid for all shared instances and rotations. | `outputs/lagos-map/src/main.js:42–43,78–82` |
| 5 | Consider pausing the render loop when the page is hidden and after motion settles; keep it active while controls, camera transitions, walking, or traffic animation need updates. | The app schedules `requestAnimationFrame(frame)` forever (`main.js:134–142`), and the loop updates all labels, traffic, controls, and renders every frame. | Medium; scheduling must resume reliably on visibility changes and user input. | `outputs/lagos-map/src/main.js:134–142` |

Already present: Three.js/esbuild bundles the app; loaded GLTF scenes are cached by path; material instances are cached by color for procedural primitives; Abuja uses instanced batches; the map is vanilla JavaScript, so React rendering overhead is not applicable. The built `dist/assets` snapshot contains 35 GLBs totaling about 3.31 MB uncompressed; this count/size does not establish the amount fetched at startup or transferred over the network. The built JS bundle is about 694 KB uncompressed. Confirm current build outputs before using these figures as release metrics.

Before choosing among these changes, capture a representative mobile and desktop browser profile: startup network requests and transfer size, scene build/loader timing, renderer draw calls and triangles, and frame time while idle and moving. That will identify which opportunities are worth implementing and establish a before/after comparison.
